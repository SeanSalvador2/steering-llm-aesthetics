# Project 19 — Anatomy of a Design Skill: Ablation + Mechanistic Interpretability of Frontend Guidance in LLMs

*Brief for a committed two-stage research project. Stage 1 is a black-box ablation of a frontend-design skill; Stage 2 is white-box mechanistic interpretability (find and causally steer the internal "design direction"). The correctness oracle is the one section that may not be weakened; everything else is the planner's to redesign and improve. 10-part schema, same as the sibling project briefs.*

---

**Seed.** LLMs produce dramatically better UIs when given a short "frontend-design skill" (a few hundred tokens of design guidance) — the community credits such skills with ending the "purple slop" aesthetic of default LLM-generated interfaces. Everyone *reports* the effect and nobody has studied it. This project studies it in **two committed stages**: **Stage 1 (black-box ablation)** — *which* pieces of the guidance carry the weight; and **Stage 2 (white-box mechanistic interpretability)** — *where and how* that guidance acts inside the model, and whether the effect can be reproduced by steering the model's activations directly, with no prompt at all.

**Why it matters.** A wide-open, right-sized question with two escalating payoffs. Stage 1 alone is a clean, useful ablation (public UI-aesthetic benchmarks are acknowledged as underdeveloped; the mechanism is unstudied). Stage 2 is the differentiated, scarce contribution — **steering-vector / activation-level interpretability pointed at UI-code generation has never been done**, and it connects directly to the mechanistic-interpretability thread running through the portfolio (the steering work in the combined-TST project, the SAE project). Together they answer both "which instruction matters" *and* "what changes inside the model when it does," which is a genuinely strong two-part paper. Composes with Project 1 (judge psychometrics supplies the eval rigor).

**Hard dependency (shapes the whole project).** Stage 2 requires **white-box access to model activations**, which means an **open-weights model you run yourself** (a Llama / Qwen / open code model) — it *cannot* be done on an API-only model. Therefore **Stage 1's ablation must run on the same open model** so the two stages study the same system; ablating one model and interpreting another would sever the link between "this instruction matters" and "here is where it lives." Pick the open model at the start and use it throughout.

**Stage 1 — the ablation (black-box).** Take the chosen open code model and a prompt set of UI generation tasks (landing pages, dashboards, forms, pricing pages). Decompose a frontend-design skill into its components — color/palette rules, spacing and visual-hierarchy rules, typography rules, component-pattern examples, negative instructions ("avoid centered purple gradients") — and ablate them one at a time and in combinations, measuring the causal effect of each on output quality. Deliverable: a ranked, quantified decomposition — which design instructions matter, by how much, and whether they're additive or interacting. This stage stands on its own as a complete result.

**Stage 2 — the interpretability (white-box, the going-all-in part).** Using the same model, investigate *where and how* the design guidance acts internally:
- **Locate the effect:** with the skill present vs. absent, find where in the model's activations the "design behavior" diverges — which layers/positions carry the signal (activation diffing, probing).
- **Extract a direction:** derive a candidate **"clean-design" steering vector** — a direction in activation space that represents the shift the skill induces (e.g. difference-in-means of activations with vs. without the guidance, or an SAE-derived feature).
- **Steer and verify causally:** add that direction at inference *with no design prompt* and test whether it reproduces the skill's quality improvement — the causal proof that you found the mechanism, not a correlate. Map where steering works and where it breaks (the honest failure surface, exactly as in the TST steering work).
- **(Optional deeper reach):** relate the located direction back to Stage 1 — do the components the ablation found most important correspond to the activation structure Stage 2 finds? A clean correspondence is the paper's strongest possible result.

**Correctness oracle (non-negotiable) — applies to both stages.** UI quality cannot be scored by eyeballing; the entire credibility rests on measurement being real. Every quality claim (ablation delta *or* steering delta) requires **two** independent signals:
- **Objective, computable metrics** from the rendered output: does it compile/render at all; accessibility-checker (WCAG) pass rate; layout metrics extractable from the rendered DOM (alignment consistency, spacing regularity, color-contrast ratios, count of overlapping/overflowing elements). Deterministic and unfoolable.
- **A pairwise preference protocol** (human and/or VLM-judge) run with the inter-rater reliability discipline from Project 1 — a delta counts only if it survives chance-corrected agreement checks and a power check.

An ablated component's effect, or a steering direction's effect, is reported as **null** if it moves neither the objective metrics nor a reliable preference delta. **Stage 2's specific bar:** a claimed "design direction" is only real if **steering it (no prompt) causally reproduces a measurable quality gain** on held-out prompts — a direction that correlates but doesn't causally steer is a hypothesis, not a finding. Aesthetic claims not backed by the objective half are inadmissible.

**Data.** Generated UI code — you produce it from the prompt set. Rendered in a headless browser (Playwright/Puppeteer) for the objective metrics. **Open-weights model run on single-GPU (Colab) — required for Stage 2's activation access.** Zero data-access risk.

**Traps.** Aesthetic evaluation is a swamp; the objective-metrics half is load-bearing and must be built and trusted first. Ablation cells multiply fast (components × combinations × prompts × seeds) — scope the factorial design deliberately. Model nondeterminism means every cell needs multiple seeds; the analysis is statistical, not anecdotal. **Stage 2 has its own risk:** the "design direction" may not cleanly exist, or may not steer causally — that null is itself a legitimate result (design behavior is distributed/not linearly steerable) and must be reported honestly rather than forced. Activation interpretability on code models is finicky; budget for the direction not being clean on the first layer/method tried.

**Creative latitude.** Beyond the optional Stage-1↔Stage-2 correspondence above: whether the winning components (and the steering direction) transfer across model families (is "good design guidance" model-specific or universal?); whether SAE-derived features give a cleaner, more monosemantic "design" feature than raw difference-in-means; whether multiple distinct design directions exist (a "spacing" direction vs. a "color" direction) mirroring the ablation components. Fable owns which of these to chase.

**`CLAUDE.md` essentials.** One open-weights model chosen at the start and used for BOTH stages — Stage 2 needs activation access, so no API-only model. Objective metrics computed on rendered DOM, never raw code strings. Every ablation cell run with ≥N seeds; report distributions, not single outputs. Preference deltas gated behind reliability + power checks (reuse Project 1 machinery). Stage 1 (ablation) is a complete standalone result; Stage 2 (interpretability) is the committed second stage, not optional. A component's OR a steering direction's effect is null until it moves an objective metric or a reliable preference. Stage 2's bar: a design direction is real only if steering it with no prompt causally reproduces a measurable quality gain on held-out prompts; report honestly if no clean steerable direction exists.
